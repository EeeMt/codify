## 分支与提交

![一条需求一条工作分支；是否创建 MR 由需求设置决定，终点都是关闭需求](assets/diagrams/zh-CN/delivery-path.svg)

同一需求使用一条工作分支 codify/issue-{id}。其中 id 是 Codify 的 Issue id，不是 GitLab issue IID。需求下的所有任务共用这条分支和同一份工作区。

第一次需要分支时，Codify 会优先使用已有的本地或远端同名分支；都没有时，从需求的「起始分支」创建，再以合并目标或项目默认分支作为后备。第一次成功推送后，分支才会出现在远端。

任务概览会显示「基线分支」「工作分支」和「目标分支」。没有关联需求的任务显示「直接推送」，来源为「手动创建」。

分析模式会丢弃改动；实施模式会提交改动；自由模式只有在 Harness 产生提交时才会交付。后续任务直接使用上一个任务留下的检出结果，包含未提交的改动。

你也可以向工作分支提交代码。远端领先时，Codify 会快进工作区；历史分叉、远端回退，或工作区带着未提交改动而远端又前进时，仓库准备会拒绝继续。先对齐分支，或在新需求上继续。

「提交记录」会分开显示「本次提交 ({count})」和「前序任务提交 ({count})」。推送结果包括：

| 结果 | 含义 |
|---|---|
| **已推送** | 分支已推送并确认 |
| **远端已包含** | 远端已有这些提交 |
| **无变更，无需推送** | 本次运行没有产生提交 |
| **未尝试推送** | 运行没有到达交付阶段 |
| **推送失败（交付未确认）** | 推送失败，或推送结果无法确认 |

推送比对规则和失败码见[《交付内部》](/guide/75-delivery-internals)。

## 合并请求

开启「创建合并请求」后，Codify 会推送工作分支，并为该需求创建或更新一条 MR；关闭时只推送分支。这个选择会随需求冻结。

任务概览会显示 !{iid} 链接、「将创建 MR」或「不创建 MR」。后续任务复用同一条 MR。Codify 初次以 Draft MR 创建并添加 Codify 标签，交付成功后移除 Draft。GitLab 管理员令牌允许模拟发起人时，MR 使用发起人身份，否则使用机器人账号。

跟踪的 MR 被合并后，GitLab Webhook 会关闭需求。手动关闭需求时可选「关闭并保留分支」或「关闭并删除分支」；需求上的分支清理设置决定 MR 自动关闭时是否删除工作分支。

「MR 流水线失败自动修复」按需求启用。只有开启、MR 正在跟踪且项目 Webhook 具备所需事件和 secret 时，系统才会创建修复任务；达到配置的次数上限后，不再为后续失败创建任务。

## 变更与用量统计

任务会记录 Git diff 事实和 Harness 上报的 Token 用量。

| 记录 | 内容 |
|---|---|
| **变更** | 新增、删除行，以及新增、修改、删除的文件数 |
| **Token 用量** | Harness 上报的输入和输出 Token |
| **运行统计** | 可用时显示时长、Token、上下文压缩和 Skill 使用次数 |

没有 diff 时显示「无净文件变化」；统计采集失败时显示「统计未采集」，不会伪装成 0。需求和统计分析只对有可用数据的已结束任务计算相应汇总。

## 运行归档

已完成和失败的任务提供「下载运行归档」。归档内容、大小上限和保留期见[《交付内部》](/guide/75-delivery-internals)。
