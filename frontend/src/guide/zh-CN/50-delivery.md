## 分支与提交

![一条需求一条工作分支；是否创建 MR 由需求设置决定，终点都是关闭需求](assets/diagrams/zh-CN/delivery-path.svg)

> [!route] **交付原则**：同一需求的所有回合共用一条工作分支；是否创建 Merge Request 只决定交付分岔，不会改变任务的执行与提交过程。

工作分支名为 `codify/issue-{id}`，其中 `id` 是 Codify 内部的 Issue id，不是 GitLab 的 issue IID。分支名只写在需求上，之后注入该需求的每个容器，因此同一需求的所有任务共用同一个名字。

系统不会提前创建工作分支。某次执行第一次需要它时，由容器内的 Worker 在本地创建：本地已有同名分支就直接检出，只有远端有该分支就基于远端分支创建本地分支，两边都没有则从基线分支新建。分支只在第一次成功推送时才出现在远端。基线分支的取值顺序是需求指定的基线分支、目标分支、项目默认分支。

任务详情页的「分支配置」区块把这条链路上的每一段列清楚：

| 字段 | 说明 |
|------|------|
| 基线分支 | 创建工作分支时使用的起始分支 |
| 工作分支 | 任务使用的工作分支，需求内所有回合共用 |
| 目标分支 | 合并请求的目标分支 |
| 直接推送 | 交付方式标记，表示代码以分支推送的形式落地 |

起始分支与仓库准备方式都配置在需求上：大型仓库可以在需求的高级设置里改「仓库克隆方式」（完整克隆 / 浅克隆）、「历史深度」和「延迟下载历史文件内容」。如果起始分支在远端不存在，系统会回退到远端默认分支并留下警告。

一个需求对应一条工作分支和一个工作区。所有任务都提交到这条分支，后续任务直接复用上一个任务留下的检出结果，不会重新克隆仓库，因此从已有的提交继续。工作区在任务之间保留，包括上一个任务还没提交的改动。分析模式的任务会丢弃改动而不提交，任务仍然算成功完成。

你和 Codify 写的是同一条分支。如果你把自己的提交推送到这条工作分支，下一次执行会快进到这些提交之上并在其上继续，不会重写或 rebase 历史。如果远端分支已经前进，而持久工作区里还有未提交的改动，仓库准备会直接拒绝，不会覆盖本地改动；两边历史已经分叉、或远端分支被回退时同样拒绝。遇到这种情况，请先在 GitLab 上把分支对齐，或在一个新需求上继续，新需求会使用全新的工作区。

「提交记录」区块展示本次执行产生的提交：

- 「本次提交 ({count})」：本次执行新增的提交，含提交 SHA 与摘要。
- 「前序任务提交 ({count})」：从工作区里继承的、尚未确认推送的前序提交。

任务执行结束时会自动把工作分支推送到远端。推送以本次执行观察到的远端位置作为比对基准（`--force-with-lease`）：只有远端仍停在该位置时才推送成功，不会使用普通的强制推送；第一次推送则要求远端分支尚不存在。

每条记录会标注推送结果：

| 推送状态 | 含义 |
|----------|------|
| 已推送 | 分支已成功推送到远端，交付确认 |
| 远端已包含 | 远端已有这些提交，无需再次推送 |
| 无变更，无需推送 | 本次执行没有产生任何改动 |
| 未尝试推送 | 执行没有走到推送阶段 |
| 推送失败（交付未确认） | 推送被拒绝或未获确认，交付不算完成 |

推送被拒绝或未获确认时，任务判定为失败，提交仍保留在工作区。失败会带上下列错误码之一：

| 错误码 | 含义 |
|--------|------|
| `remote_diverged` | 远端分支已移动，本地与远端互不包含；不做合并，直接拒绝 |
| `remote_rewound` | 远端分支不再包含本次执行开始时的提交 |
| `remote_deleted` | 执行开始后远端分支被删除 |
| `remote_changed` | 推送被拒绝，复查时远端分支又发生了变化 |
| `branch_changed` | 收尾期间本地分支发生了变化 |
| `history_rewritten` | 分支历史与记录的起点不再一致 |
| `history_unverifiable` | 无法在本地确认祖先关系（通常是浅克隆），因此没有尝试推送 |
| `push_failed` | 推送被拒绝，且远端分支没有变化 |
| `remote_unconfirmed` | 推送后无法确认远端状态，交付不算完成 |

界面会原样显示原始错误文本，不做翻译。

任务如果在 Worker 提交残留改动之前就失败，脏工作区会留给下一个任务：下一次执行开始时这些文件仍在工作区里，可能随本次改动一起提交，因此下一个任务的 diff 里可能包含并非它产生的内容。

提交信息由模型根据改动文件与 diff 统计生成。实施模式若未开启「要求代码变更」，没有改动也能以「无变更，无需推送」收尾；开启后则会直接失败。

## 合并请求

交付以 Merge Request 为主。任务的「合并请求」区块给出 MR 地址与 MR 标题，创建状态有三种：

- 已创建：MR 已存在，点击地址可跳转到 GitLab。
- 待创建：任务尚未完成交付，MR 还未生成。
- 不创建 MR：创建任务时关闭了「创建合并请求」，只推送工作分支。

创建任务时的「MR 设置」用「创建合并请求」开关控制这一点：开启时显示「将创建 MR」，关闭时显示「不创建 MR」，并说明「禁用时仅推送分支，不创建 MR」。需求详情页的「交付概览」用「代码交付」汇总这一状态，显示「已生成 MR」或「等待交付」。

MR 的生命周期由 Codify 自动管理：执行开始时会先创建一条 Draft MR，任务成功交付后去掉 Draft 标记，并用需求标题和需求下全部回合的交付摘要重写标题与描述。工作分支是 MR 的源分支，需求变更目标分支不会创建新的 MR，而是复用该分支上已打开的那一条。

关闭需求时，界面会提示请选择如何处理工作分支，可选「关闭并保留分支」或「关闭并删除分支」；删除操作不可撤销。如果开启了「分支清理」，MR 合并触发的 webhook 自动关闭需求时会删除 AI 工作分支；未开启则保留。

## 变更与用量统计

每个任务会记录两类量化指标，它们同时进入仪表盘与统计分析的趋势图。

**代码变更**来自执行过程中采集的 diff 事实，包含新增、删除、总行数，以及新增 / 修改 / 删除的文件数。任务列表与详情页把它显示为 `+新增 -删除`，无文件净变化时显示「无净文件变化」。如果这次执行没有采集到统计，会显示「统计未采集」，而不是显示零。

**Token 用量**来自 Harness 上报的用量事件，分为「输入」与「输出」两项，显示在任务详情页的「Token 用量」区块。结构化事件流中，子代理会单独标注各自的 Token 消耗；发生「上下文已压缩」时还会记录压缩次数（形如 `{count}次`）。「运行统计」区块汇总这次执行的时长、模型与实际用量。

需求详情页会把同一需求下所有回合的统计累加，分别给出新增行数、删除行数、输入 Token 与输出 Token 四个总量，方便判断一条需求整体的代价。

历史任务（在用量采集上线前创建的）不显示 Token 字段。任务状态被手动修正时不会重算 Token 与代码变更数字，因此统计数据反映的是实际执行结果。

两项统计都在任务收尾时写入：任务仍在执行中时，详情页对应位置为空；任务列表也支持按「变更」与「耗时」排序，方便找出代价最大的执行。

## 运行归档

「运行归档」可以下载这次运行的完整证据包，用于复现问题和归档排查。点击「下载运行归档」获取 `task-{id}-runtime-archive.tar.gz`，这是一个 gzip 打包的 tar 文件。

归档由容器在进程退出时从本次运行的临时目录 `/tmp/codify-runtime` 封装生成，因此只要任务收尾就会生成，无论结果是成功、失败、取消还是超时；随后由后端把它流式写入控制机上的归档存储 `/opt/codify-archives`。任务仍在执行时没有归档，下载入口不可用。下载失败时页面会给出对应提示。

归档按条目收集，存在才收录，不存在则跳过，因此提前结束的执行会得到更小的归档：

| 文件 | 内容 |
|------|------|
| `event.jsonl` | 规范化事件流，界面「事件流」页签的数据来源 |
| `opencode-http-audit.jsonl` | HTTP 审计记录，只有 OpenCode 运行会产生 |
| `harness-result.json` | Harness 最终结果 |
| `runtime.json` | 运行时信息，含实际使用的模型；由 Claude 的 runner 写入，其他 Harness 不产生该文件 |
| `console.log` | 容器控制台原始输出 |
| `delivery-summary.md` | 交付摘要 |
| `delivery-summary-validation.json` | 交付摘要校验结果 |
| `repository-preparation.json` | 仓库克隆与准备的遥测数据 |
| `artifacts-validation.json` | 制品收集与封装的校验结果 |
| `harness-events/` | 本次使用 Harness 的原始事件流，命名为 `claude.jsonl`、`codex.jsonl`、`pi.jsonl` 或 `opencode.jsonl`；`claude.jsonl` 每次运行都会预创建，未使用 Claude 时为空文件 |
| `artifacts/` | 本次运行的用户制品，封装后原样收录 |

面板上的说明只列出常见的几项：`console.log`、`repository-preparation.json`，以及进入 AI 执行阶段后才会有的 `event.jsonl` 和 `runtime.json`。

其余临时文件不会进归档：提示词文件、制品策略、前置与后置脚本、编排用的运行时包（Runtime Bundle）和超时标记都不在其中；工作区与 Git 仓库本身不打包，`claude/` 与 `shared/` 挂载上的 Harness 状态目录也不打包，归档只收录本次运行写进自己临时目录的内容。

归档整包有 640 MiB 的硬上限。封装失败，或加入 `artifacts/` 后会超过上限时，会省略用户制品目录，并在 `artifacts-validation.json` 中记录省略原因。封装时生效的制品预算默认为总数 200 MiB、单文件 100 MiB、条目 5,000 个，可由管理员调整。

归档默认保留 30 天，按归档记录的创建时间计算。过期后会被自动清理，再次下载会提示「文件已过期」，此时仍可查看任务本身记录的事件流与元数据。删除归档不会删除任务记录。

日志面板里的「原始日志」在内容过大时只渲染最近片段，此时归档是获取完整输出的可靠途径。

如果同一份文件能以结构化数据获取（例如某次工具调用的输入或输出），过程面板可以直接加载；数据不可再取到时该路径提示「加载内容失败」，加载归档数据时显示加载中状态。
