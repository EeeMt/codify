## 先看这个例子

下面用一个虚构仓库演示一轮完整流程：给登录接口补一个“过期 token 返回 401”的测试。你的文件和接口名称可能不同，创建任务时换成项目里的实际内容。

需求描述保存跨回合仍成立的背景，任务提示词定义本回合要做的事。

## 先创建需求

| 字段 | 示例填写 | 为什么这样填 |
|---|---|---|
| 标题 | 登录接口补充过期 token 测试 | 让需求标题能直接说明要解决的问题 |
| 描述 | 登录接口对无效凭据返回 401。成功登录的响应和现有鉴权规则保持不变。 | 这是后续回合仍然需要遵守的背景 |
| 项目 | `acme/auth-service` | 选择实际要修改的 GitLab 项目 |
| 起始分支 | `develop` | 从当前开发基线创建工作分支 |
| 合并目标 | `develop` | 让 Merge Request 回到同一条开发分支 |
| 创建合并请求 | 开启 | 需要团队评审代码 |
| 分支清理 | 按团队习惯选择 | 合并后决定是否删除 AI 工作分支 |
| Worker | 已验证且包含目标 Harness 的 Worker | 创建后不能更换，先确认运行环境可用 |

提交前检查项目、分支、合并目标、Worker 和高级设置。创建需求后这些设置会冻结。

## 再写任务提示词

在需求详情页点击「创建任务」，选择「实施模式」和「立即执行」。需求描述会先填入提示词，下面这份内容可以直接替换它：

```text
目标：为登录接口补充过期 token 的失败场景测试，并提交代码。

范围：先检查现有登录接口、鉴权中间件和测试目录；只修改与该场景直接相关的实现或测试文件。

约束：成功登录和其他已有错误响应保持不变；沿用项目现有的测试框架和断言风格；不要修改数据库结构。

验收标准：
- 过期 token 请求返回 HTTP 401；
- 测试能稳定复现这个结果；
- 现有登录相关测试继续通过；
- 形成清晰的提交说明。

验证方式：运行登录模块的定向测试，再运行项目文档中要求的完整测试命令；在结果中报告命令和关键输出。
```

这份提示词给 Harness 一个结果、一个边界和一组检查。文件名和测试命令已知时直接写出；不确定时让 Harness 先检查仓库。

## 运行、检查、继续

提交任务后按这个顺序看结果：

1. 在任务详情页看「事件流」，确认它完成了仓库检查、修改和验证。
2. 需要完整输出时再打开「原始日志」或下载运行归档。
3. 任务完成后检查「提交记录」和「交付结果」，再打开 Merge Request 评审。
4. 如果只缺一项测试或文档，在同一需求上「追加任务」，明确写出剩余工作；不要为同一个分支另起一个需求。
5. 如果要换项目、起始分支、合并目标或 Worker，结束当前需求后新建需求。

| 结果 | 下一步 |
|---|---|
| 测试通过，提交和推送都成功 | 评审并合并 Merge Request |
| 代码正确，但漏了一个测试 | 追加任务，只写缺少的测试和验证命令 |
| 因配额、运行时或网络暂时失败 | 先看失败原因，修复条件后重试 |
| 任务提示词写错，范围需要重定 | 追加任务或修正后重试，不要把错误提示词当成需求背景 |

## 这个例子为什么这样写

需求描述没有塞入某一次测试的文件名和命令，因此后续任务仍能复用它。任务提示词则把当前回合的结果写成可检查的条件，Harness 可以据此安排检查、修改和验证。若任务使用自定义运行指令，还要确认模板包含 `{{user_prompt}}`，否则这段提示词不会自动进入最终运行提示词，详见[《创建任务》](/guide/30-create-task)。
