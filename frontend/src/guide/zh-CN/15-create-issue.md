## 先决定新需求还是追加任务

`Issue` 是一条持续工作的容器，负责保存项目、工作区、工作分支、Worker 和交付策略。`Task` 是这条工作线上的一次执行回合。继续任务可以沿用当前会话，也可以开启新会话；新会话仍然留在同一个需求、工作区和分支上。

| 现在要做的事 | 选择 |
|---|---|
| 换项目、起始分支、合并目标、Worker、克隆方式或 MR 策略 | 新建需求 |
| 需要一条独立的工作分支或独立 Merge Request | 新建需求 |
| 仍在同一项目和分支策略下推进下一步 | 追加任务 |
| 只是不满意上一次结果，想补一处修改或再跑一次验证 | 追加任务 |

需求创建时会固定项目、起始分支、合并目标、「创建合并请求」、「分支清理」、Worker 和仓库克隆设置。标题、描述、「MR 流水线失败自动修复」、默认 AI Provider 和默认 Harness 可以在需求详情页调整；已创建的任务不会因此改变。

> [!warning] **提交前确认**：项目、起始分支、合并目标、MR 开关、分支清理、Worker 和克隆方式。它们创建后不能修改，需要换这些边界时请新建需求。

创建需求不会自动创建任务。提交后到需求详情页发起第一个任务；分析模式可以只输出分析，不修改代码。具体操作见[《创建任务》](/guide/30-create-task)。

## 表单字段 {deep}

![表单分五个部分，创建前先确认边界和交付方式](assets/diagrams/zh-CN/create-issue-form.svg)

表单分为项目、需求内容、分支策略、运行环境和高级设置。项目、标题、起始分支、Worker 是必填项。其余字段按下面的作用理解即可：

| 字段 | 作用 | 创建后 |
|---|---|---|
| 项目 | 选择要修改的 GitLab 项目。列表只显示当前登录身份可访问的项目 | 固定 |
| 标题 | 需求名称，也会作为 Merge Request 标题的来源，通常显示为 `Draft: 标题` | 可改 |
| 描述 | 保存跨任务都成立的目标、背景和约束；创建任务时预填到任务提示词 | 可改，仅影响之后创建的任务 |
| 起始分支 | Worker 拉取代码的基线，默认取项目默认分支 | 固定 |
| 创建合并请求、合并目标 | 决定是否创建或更新 MR，以及工作分支合入哪条分支。关闭 MR 时合并目标不可用 | 固定 |
| Worker | 执行这条需求的 Worker 配置 | 固定 |
| 默认 Provider、默认 Harness | 为新任务提供默认模型服务和 Harness；任务可按规则覆盖 | 可改默认值 |
| 高级设置 | 完整或浅克隆、`blob:none`、分支清理和 CI 自动修复 | 克隆与分支清理固定；CI 开关可改 |

浅克隆和延迟下载历史文件内容只支持[《平台参考》](/guide/96-platform-reference)列出的挂载 Worker Kit。默认完整克隆最稳妥；不确定仓库是否需要完整历史时，先保留默认值。CI 自动修复还要求开启 MR，且项目 Webhook 检查通过。

## 描述怎么写

需求描述放长期背景，任务提示词放本回合的具体工作。描述适合写目标、固定约束、不变规则和相关链接；提示词适合写本次要改什么、允许改哪里、做到什么程度，以及如何验证。

描述会作为新任务提示词的初始内容，但创建后修改描述不会回写已有任务。描述为空也可以先创建需求，再到详情页写第一条任务。

可以从模板库填充描述。模板里的 `{{变量}}` 不会自动替换，提交前要换成实际内容；选择模板会替换整段已有描述，已有内容时请确认提示。

标题会出现在需求列表和 MR 中，建议写成可判断结果的一句话。描述使用 Markdown 即可，列表比大段背景更容易在需求详情页回看。

```text
目标：

长期约束：

完成后应满足：
```

本回合的文件范围、验收标准和验证命令写在[《创建任务》](/guide/30-create-task)的任务提示词中。

## 分支与交付设置

工作分支的路径是：`起始分支` → `codify/issue-{id}` → `合并目标`。其中 `codify/issue-{id}` 由 Codify 在创建需求时确定，首个任务推送提交后才会在 GitLab 中出现。一个需求下的后续任务继续使用这条分支。

- 开启「创建合并请求」：任务推送工作分支，并创建或更新指向合并目标的 MR。
- 关闭「创建合并请求」：任务仍推送工作分支，但不会创建 MR，合并目标也不生效。
- 开启「分支清理」：MR 合并的 Webhook 自动关闭需求时删除工作分支。手动关闭需求时，页面会单独询问保留还是删除。

起始分支和合并目标通常都选项目默认分支；只有代码从一条分支开始、最终要合入另一条分支时才分开设置。浅克隆和延迟下载内容会降低初始化成本，但依赖 blame、merge-base 或旧提交的任务应使用完整克隆。

也可以从另一条需求的 `codify/issue-{id}` 分支起步。这样只继承提交，不继承源需求的工作区和会话；源分支还必须在新需求的首个任务运行时存在。更多组合方式见[《使用技巧》](/guide/78-techniques)。

## 创建之后

提交成功后会进入需求详情页。新需求状态为「待处理」，此时还没有任务，工作分支名称已经分配，但尚未克隆或推送代码。

1. 点击「创建任务」，选择任务模式和优先级，再立即执行或预约执行。
2. 在需求详情页查看任务状态、事件、日志、提交和交付信息。
3. 结果需要调整时追加任务；项目或固定分支策略改变时新建需求。

需求详情页可以修改标题、描述、CI 自动修复、默认 Provider 和默认 Harness。关闭需求时选择保留或删除工作分支；删除需求会连同记录一起移除，不能撤销。

## 常见问题

| 现象 | 先检查什么 |
|---|---|
| 项目列表为空 | 当前登录身份是否能访问项目；机器人账号与 GitLab 登录用户看到的项目范围可能不同。见[《故障排查》](/guide/55-troubleshooting) |
| 分支列表加载失败 | 刷新后重试；持续失败时检查 GitLab 连接和令牌 |
| 没有可选 Worker | 管理员是否启用了 Worker 配置；Worker 是创建需求的必填项 |
| 浅克隆或延迟下载不可选 | 当前 Worker 是否为挂载模式且达到[《平台参考》](/guide/96-platform-reference)的最低版本 |
| CI 自动修复不可用 | 是否开启 MR，以及项目 Webhook 是否通过配置检查 |
| 提交后提示 Worker 或 Provider 不可用 | 选择仍处于启用状态的配置，或把 Provider 改回系统默认 |

如果只是想改变任务模式、优先级、预约时间或本回合提示词，不需要新建需求，直接从需求详情页创建或追加任务即可。
