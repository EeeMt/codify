## 什么时候要新建需求

需求（Issue）是 Codify 的工作单元，也是**工作区、AI 会话与分支**的所有者：一个需求持有一条工作分支 `codify/issue-{id}`、一份工作区和一个 AI 会话，最终汇成一个 Merge Request。这些资源都挂在需求上，「新建需求」与「追加任务」是两个不同的操作。

- **创建后不可修改**：项目、起始分支、合并目标、Worker，以及仓库克隆设置。
- **创建后仍可修改**：标题、描述、「MR 流水线失败自动修复」和「默认 AI Provider」。
- **一个需求一条工作分支、一个 Merge Request**；同一需求内的任务按回合串行，只有队首任务会真正运行。
- **「追加任务」共享同一工作区、AI 会话与 Git 分支**，可以接着上一次任务停下的位置继续。

> [!warning] **创建前先决定**：项目、起始分支、合并目标、Worker 和仓库克隆设置会随需求冻结；如果这些条件不同，直接新建需求更清楚。

| 情形 | 原因 |
|------|------|
| 换了一个 GitLab 项目 | 项目在创建需求时确定，之后不可修改 |
| 换了一条起始分支或合并目标 | 分支策略在创建需求时确定，之后不可修改 |
| 想要一个独立的 Merge Request | 一个需求一个 MR，合并目标不同的工作应各自成需求 |
| 需要与现有需求并行推进 | 同一需求内的任务按回合串行，只有队首任务会真正运行 |
| 需要不同的 Worker 或仓库克隆策略 | Worker 与克隆设置在创建需求时冻结，之后不可修改 |

本页只创建需求，不创建任务：第一个任务要到需求详情页上另外发起，见《创建任务》。需求也不要求立刻有代码变更——把第一个任务建成分析模式同样可以挂在需求上，此时任务只输出分析、不修改文件。

## 表单字段

![表单分五个部分，创建后能改的只有少数几项](assets/diagrams/zh-CN/create-issue-form.svg)

表单最下面是可折叠的「高级设置」，以及「重置」和「创建需求」两个按钮。需求创建后，这些设置成为它的任务默认值：Worker、默认 AI Provider、默认 Harness 与仓库克隆设置由所有任务继承，单个任务可以在创建时覆盖其中可覆盖的部分。标着「必填」的字段必须先选好，否则提交会被拦下。

### 项目

| 标签 | 作用 | 默认 | 作用域 |
|------|------|------|--------|
| 项目 | 需求所属的 GitLab 项目；以卡片网格选择，卡片显示项目名、命名空间与项目描述 | 未选中，必填 | 需求 |
| 搜索项目... | 按项目名、命名空间或描述过滤卡片；最近用过的项目排在前面并标出「最近使用」 | 空 | 需求 |

列表只包含平台当前能看到、且平台有权访问的项目。列表为空时显示「未找到项目」，加载失败时提示「获取项目失败」；两种情况都先看《故障排查》。

### 需求内容

| 标签 | 作用 | 默认 | 作用域 |
|------|------|------|--------|
| 标题 | 需求的名称；合并请求标题取自它，格式为 `Draft: 标题`，超过 120 个字符会被截断 | 空，必填；输入时会给出最近用过的标题建议 | 需求 |
| 描述 | 这个需求要做什么；作为创建任务时的默认提示词 | 空 | 需求，任务继承 |
| 使用提示词模板 | 打开「选择模板」抽屉，从模板库挑选内容填入描述；可用「按标签筛选」缩小范围 | 不套用模板 | 需求 |

模板库为空时抽屉显示「暂无可用提示词模板」，筛选无结果时显示「没有匹配所选标签的模板」。描述里已有内容时选择模板会先确认「当前描述内容将被模板替换，是否继续？」。

### 分支策略

这一组决定代码从哪里来、到哪里去，按顺序是：**起始分支**（AI 从此拉取）→ **AI 工作分支（自动生成）**（即 `codify/issue-{id}`）→ **MR 合并入** → **合并目标**。这一组的最上方用一条流程示意把这条路径画出来，关闭「创建合并请求」后后半段会变灰。

| 标签 | 作用 | 默认 | 作用域 |
|------|------|------|--------|
| 起始分支 | 需求工作分支的基线；Worker 从它拉取代码，再创建新的工作分支。「AI 将基于此分支拉取代码，并创建新的工作分支进行开发。」 | 项目默认分支，切换项目后自动选中 | 需求，创建后不可修改 |
| 创建合并请求 | 开关。开启后任务产出提交时会创建 Merge Request；关闭后只推送工作分支。开关右侧直接显示结果：「将创建 MR」或「不创建 MR」 | 开启（将创建 MR） | 需求 |
| 合并目标 | 工作分支通过 Merge Request 合并入的目标分支；「AI 完成开发后，工作分支将通过 Merge Request 合并入此分支（通常为 main / master / dev / develop）。」关闭「创建合并请求」后不可选，占位符显示「不创建 MR」 | 项目默认分支，开启 MR 时自动选中 | 需求，创建后不可修改 |
| 使用起始分支 | 把当前「起始分支」一键填进「合并目标」 | — | —（按钮） |

「起始分支」和「合并目标」由同一份分支列表选择，都支持筛选。两个下拉都依赖项目：没有选项目时处于禁用状态。分支列表加载失败会提示「获取分支失败」，此时选不了分支也提交不了。

### 运行环境

| 标签 | 作用 | 默认 | 作用域 |
|------|------|------|--------|
| Worker | 执行这套需求的 Worker 配置；「创建后不可修改；任务按该 Worker 执行。」 | 未选中，必填，占位符「请选择 Worker」 | 需求，创建后不可修改 |
| 默认 AI Provider | 需求的任务默认使用的模型服务。下拉列出启用中的 Provider（默认项带 ★ 标记）；清空即回到系统默认，占位符「系统默认」 | 系统默认 Provider | 需求，创建后可在需求详情中修改 |
| 默认 Harness | 新会话任务默认使用的 Harness；可选值来自所选 Worker 启用的 Harness 列表（Claude、Codex、Pi、OpenCode）。「新会话任务时可修改；留空则跟随 Worker 默认。」 | 所选 Worker 的默认 Harness；未选 Worker 时该下拉禁用，占位符「跟随 Worker 默认」 | 需求，任务继承 |

这一组的说明文字是「Worker 为必填项并由需求固定；AI Provider 可使用系统默认配置。」三者关系是：Worker 一旦选定就跟着需求走，模型服务有需求级默认值也有系统级兜底，Harness 跟着 Worker 走。

选中 Worker 会把它启用的 Harness 填入「默认 Harness」并预选该 Worker 的默认值；如果该 Worker 没有启用任何 Harness，下拉为空。

### 高级设置

「高级设置」默认折叠，标题旁给出当前取值摘要；点开后才显示下面的字段。提交时若有字段校验不通过，页面会自动展开这一段并把焦点移到出错字段。

| 标签 | 作用 | 默认 | 作用域 |
|------|------|------|--------|
| 仓库克隆方式 | 选择「完整克隆」（获取完整提交历史；适合依赖 blame、merge-base 或旧提交的任务）或「浅克隆」（仅获取指定数量的近期提交，降低大型仓库首次初始化耗时） | 完整克隆 | 需求，创建后不可修改 |
| 历史深度 | 浅克隆保留的近期提交数，取值 1 到 10000 的整数，非法值提示「历史深度必须是 1 到 10000 之间的整数」 | 选择浅克隆时自动填 50 | 需求，创建后不可修改 |
| 延迟下载历史文件内容 | 开关。开启后启用 blob:none，按需获取未下载的文件内容；关闭则 clone 时直接取回所需文件内容 | 关闭 | 需求，创建后不可修改 |
| 分支清理 | 「MR 合并 webhook 自动关闭需求时，将删除 AI 工作分支」；关闭后改为「MR 合并 webhook 自动关闭需求时，将保留 AI 工作分支」 | 开启（自动删除分支） | 需求 |
| MR 流水线失败自动修复 | 「跟踪的 MR 流水线失败时，Codify 会自动创建修复任务」；关闭时「流水线失败会被记录，但不会自动创建修复任务」 | 关闭 | 需求 |

- **仓库克隆的两项设置受 Worker 能力限制。** 浅克隆与延迟下载历史文件内容只支持「挂载 Worker Kit」的 Worker，且 Worker Kit 版本需为 0.3.0 或更高。不满足时浅克隆选项直接禁用，界面给出原因：「浅克隆和延迟下载历史文件内容仅支持“挂载 Worker Kit”的 Worker；镜像内置 Worker 不支持。」或「当前 Worker Kit 版本不支持浅克隆或延迟下载历史文件内容，请升级到 0.3.0 或更高版本。」折叠标题上的「仓库克隆」摘要会一直显示当前策略（完整克隆，或浅克隆 · depth 50 这样的形式）。
- **「MR 流水线失败自动修复」还取决于另外两个条件。** 只有开启「创建合并请求」、且所选项目的 Webhook 配置检查通过时才能打开；否则开关禁用，说明文字给出「不可用：」加原因，原因可能是「项目 Webhook 尚未配置」「缺少 Webhook 验证密钥」「未启用 SSL 验证」「未启用合并请求事件」「未启用流水线事件」或「无法确认 Webhook 配置状态」。关闭「创建合并请求」时，该开关会自动回到关闭。

## 描述怎么写

描述会作为这个需求创建任务时的默认提示词，也就是 Harness 实际收到的需求内容。它决定任务能不能一次做对，值得多花几分钟：

- **写目标，也写边界**：要改什么、不要改什么、必须保持哪些行为不变。含糊的目标通常换来一次需要重试的任务。
- **写验收标准**：什么算完成，最好给出可验证的判断依据，例如某个接口的行为、某个测试要过。
- **描述可以为空**，但留空之后每次创建任务都要自己重写提示词；把稳定的背景放进描述更省事。
- **描述随时可改**，需求详情页的「编辑需求」可以更新它，改动只影响之后创建的任务。

用「使用提示词模板」可以从模板库挑一份现成的写法，按标签筛选后选中即可填入。

- 模板里的 `{{变量}}` 是占位符，**不会自动替换**。编辑器会检测到它们并提示「请替换模板中的变量」，变量面板同时列出「变量说明」；把占位符换成实际内容再提交。
- 描述里已有内容时套用模板会整体覆盖，界面先确认「当前描述内容将被模板替换，是否继续？」。

标题同样会外显：它是合并请求标题的来源（`Draft: 标题`），所以写得像一句结论，比写得笼统更有用。描述里的内容在需求详情页按 Markdown 渲染，可以用列表和代码块把关键信息排清楚。

## 分支与交付设置

**起始分支是拉取代码的基线，合并目标是工作分支的归处。** 工作分支从起始分支派生，合并目标也就是 Merge Request 的目标分支。两者通常都取项目默认分支，但也可以不同：例如从 `develop` 拉取、往 `main` 合并，或从 `main` 拉取、往 `release` 合并。表单里的流程示意把这条链路固定下来：`起始分支` → `AI 工作分支（自动生成）` → `合并目标`。

**「创建合并请求」决定这条链路的终点是否存在。** 开启时，任务产出提交后会推送工作分支、创建（或复用）一条 Merge Request，并把它指向「合并目标」；关闭时，工作分支照常推送，但不会创建 Merge Request，「合并目标」不参与，也不生效。MR 以一个需要复核的草稿开始，代码变更摘要与提交记录会随任务推进写进它的描述。

**工作分支名在创建需求时就固定了：`codify/issue-{id}`。** `{id}` 是需求编号，所以同一个需求的所有回合都落在同一条分支上；这条分支在 GitLab 上真正出现，是在第一个任务推送提交时。这也是「追加任务」能接着上次继续的原因。

「分支清理」只作用于自动关闭场景：需求因 MR 合并而被 Webhook 自动关闭时，开启则删除这条工作分支，关闭则保留。手动关闭需求时会单独询问「请选择如何处理工作分支 "{branch}"。」，选项是「关闭并保留分支」或「关闭并删除分支」，与这个开关无关。

**仓库克隆设置只影响初始化成本。** 大型仓库首次初始化往往卡在克隆上，因此可以选「浅克隆」只取回近期历史，或用「延迟下载历史文件内容」按需取文件内容。默认的「完整克隆」最稳妥，依赖 blame、merge-base 或旧提交的任务必须用它。这两项都要求挂载模式的 Worker Kit 0.3.0 或更高版本，且**创建后不可修改**，只能在新建需求时决定。

## 创建之后

提交成功后页面跳转到需求详情页 `/issues/{id}`，需求以「待处理」开局。此时它还没有任何任务：执行区显示「尚未执行」，页头的主按钮此时是「创建任务」，有了任务之后才变成「追加任务」。

1. **发起第一个任务**。在需求详情页点「创建任务」，选择任务模式与优先级后执行或预约。分支在第一个任务推送提交时真正落到 GitLab 上。
2. **跟踪执行**。详情页的「当前执行」与「执行记录」展示每个回合的结果；「交付概览」汇总代码交付状态，并依据是否已有合并请求显示「已生成 MR」或「等待交付」。
3. **按需修改需求**。「编辑需求」可以改「标题」「描述」「MR 流水线失败自动修复」与「默认 AI Provider」；「Worker」在编辑弹窗里是只读的。

因此**创建后不可修改**的设置只能靠新建需求重来，它们恰好决定了工作分支、工作区与容器环境，一旦有任务跑过，改它们就等于换一条流水线。

需求的生命周期还有两个出口：

- **「关闭需求」** 结束这条需求，并询问工作分支的去留（保留或删除）。
- **「删除需求」** 连同记录一起移除，不可撤销。

如果开启了「MR 流水线失败自动修复」，需求详情页还会多出一块「CI 自动化」，显示「失败流水线」「最近状态」「修复任务」与「根因 Job」等信息，并可以跳到自动创建的修复任务。

## 常见错误

| 现象或提示 | 原因 | 处理 |
|------------|------|------|
| 项目列表为空，显示「未找到项目」 | 平台看不到任何项目：GitLab 机器人账号不是项目的成员，项目也不是内部或公开可见 | 让管理员把机器人账号加进项目，并给它推送分支与创建合并请求所需的权限；见《故障排查》 |
| 提示「获取项目失败」 | 项目列表接口失败，通常是 GitLab 连接或令牌问题 | 联系管理员检查 GitLab 连接 |
| 想要的项目不在列表里 | 当前账号或机器人账号访问不到它 | 见《故障排查》的权限与登录问题一节 |
| 提示「获取分支失败」 | 分支列表接口失败；此时「起始分支」为空，无法提交 | 刷新页面重试；持续失败联系管理员 |
| 提示「请选择项目」 | 没有选中项目卡片 | 先选项目，其余字段大多依赖它 |
| 标题一栏报错并显示「标题」 | 标题为空 | 填写标题 |
| 提示「选择起始分支」 | 未选中起始分支，通常是项目没选或分支列表还没加载完 | 选好项目与起始分支 |
| 提示「请选择 Worker」 | 没有选中 Worker | 选一个 Worker；下拉为空说明管理员没有启用任何 Worker 配置，需要联系管理员 |
| 提示「历史深度必须是 1 到 10000 之间的整数」 | 浅克隆的历史深度非法 | 改成 1 到 10000 之间的整数 |
| 选不了「浅克隆」，或出现「仅支持“挂载 Worker Kit”的 Worker」「请升级到 0.3.0 或更高版本」 | 所选 Worker 是镜像内置模式，或 Worker Kit 版本低于 0.3.0 | 换一个挂载模式且版本足够的 Worker，或保留「完整克隆」 |
| 「MR 流水线失败自动修复」开关禁用，提示「不可用：」加原因 | 未开启「创建合并请求」，或项目 Webhook 检查未通过 | 按提示补齐 Webhook 配置，或先开启「创建合并请求」 |
| 点「创建需求」没有反应 | 校验未通过 | 页面会滚动到出错字段并展开「高级设置」，按红色提示修正 |
| 提交后提示 Worker 不可用，或 `Worker profile is not available` / `Default AI provider is not available` | 所选 Worker 被禁用，或所选 Provider 已被禁用或删除 | 重新选择可用的 Worker 与 Provider，或改用「系统默认」 |

平台侧的失败信息在写入前会经过敏感数据脱敏，`glpat-*` 令牌与 `sk-ant-*` 密钥不会出现在错误摘要中。
