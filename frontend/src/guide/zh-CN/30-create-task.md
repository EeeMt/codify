## 从哪里发起任务

任务总是属于某条需求。需求详情页的「创建任务」用于第一回合，「追加任务」用于继续推进；最新任务还会提供「追加后续任务」，失败或取消的任务可以「重试」。创建需求页也能填写需求并发起第一个任务，旧路径 `/create-task` 会重定向到 `/issues/create`。

创建抽屉分为「任务内容」和「执行设置」。提示词是本回合发给 Harness 的输入：需求有描述时会先填入，你可以按当前任务改写。使用提示词模板会替换现有内容，页面会先要求确认。

项目和分支属于需求，不属于单个任务。任务创建时会把 Worker 和模型服务身份写入一个 **frozen snapshot**，之后修改配置不会影响这次任务。

| 需求决定 | 任务决定 |
|---|---|
| 项目、起始分支、工作分支、合并目标、Worker、MR 策略 | 提示词、任务模式、优先级、执行时间 |
| 工作区和分支的持续关系 | 本回合是否继续会话，以及是否覆盖允许覆盖的默认值 |

## 任务模式

![模式决定是否改代码，时机决定何时排队](assets/diagrams/zh-CN/task-mode-choice.svg)

从「选择任务模式」开始，再进入完整表单。模式决定这次任务要产出什么：

| 模式 | 适合做什么 | 代码变更 |
|---|---|---|
| 实施模式 | 调查项目、修改文件并提交结果 | 可以要求必须有提交 |
| 分析模式 | 回答问题、调查现状、给出方案 | 不修改文件 |
| 自由模式 | 只把任务提示词交给 Harness，由它决定处理方式 | 不承诺提交 |

「要求代码变更」只对实施模式生效。开启后没有代码提交会判为失败；新任务默认关闭。分析模式和自由模式会自动关闭这个开关。模式会冻结在任务上，重试沿用源任务模式，CI 自动修复任务固定为实施模式并要求代码变更。

## 任务提示词怎么写

任务提示词只写本回合要完成的事。先写目标和结果，再补范围、约束、验收标准与验证方式。文件名、接口名和错误信息已知就直接写；一个任务尽量只对应一个可验收结果，下一件事用追加任务继续。

| 内容 | 要回答的问题 |
|---|---|
| 目标 | 这一次要得到什么结果？ |
| 范围 | 可以检查或修改哪些文件、模块或接口？ |
| 约束 | 哪些行为必须保持不变？ |
| 验收标准 | 什么现象能证明任务完成？ |
| 验证方式 | 运行哪些测试、命令或检查？ |

```text
本回合目标：

允许修改：

保持不变：

验收标准：

验证方式：
```

需求描述适合放长期背景，任务提示词适合放本回合内容。完整字段示例见[《完整示例》](/guide/12-complete-example)。分析模式写问题、调查范围和期望输出；实施模式补充代码结果和验证方式；自由模式说明期望结果即可。

### 提示词如何到达 Harness

![从需求背景到 Harness 实际收到的最终运行提示词](assets/diagrams/zh-CN/prompt-pipeline.svg)

任务提示词通过运行指令模板中的 `{{user_prompt}}` 进入 Harness。模板还可以加入 `{{issue_title}}`、`{{branch_name}}` 等上下文。保存任务时，模板按当前值渲染成「最终运行提示词」，并随任务冻结。自定义模板漏掉 `{{user_prompt}}` 时，页面会提示任务提示词不会自动传入。

## 优先级

优先级决定不同需求之间谁先获得 Worker，不改变同一需求内的顺序。新任务默认是 P1：

| 值 | 含义 | 适合 |
|---|---|---|
| P0 | 紧急 | 阻塞发布或需要立即处理的问题 |
| P1 | 普通 | 日常功能和改进 |
| P2 | 低 | 可以等待的重构和小优化 |

调度器按 P0、P1、P2 选择可执行的需求队首；同一需求只有队首会参与派发。因此 P2 队首会等待其他需求的 P0 或 P1 队首。状态为 Pending 或 Queued 的任务可以通过「编辑任务」调整优先级。

## 立即执行或预约执行

「立即执行」会在创建后进入队列；「定时执行」会在指定时间进入队列。预约时间必须晚于当前时间，页面按 UTC+8 展示确认时间。

启用时段容量后，「近 7 日预约热力图」会显示负载，颜色越深表示已预约任务越多。接近或达到容量时页面会提示；强制容量已满时不能提交，改期也会重新检查。

预约不会绕过需求队列。排在前面的任务未完成时，后续任务即使到了预约时间也会等待。待执行任务可以用「立即执行」提前进入自己的可执行状态，或用「修改预约」调整时间。

## 运行指令与变量

「运行指令模板」位于「高级」中，用来组装任务提示词和上下文。编辑器提供「指令」和「预览」页签，可以插入变量、刷新预览或恢复当前模式的默认模板；渲染结果会保存为任务的「最终运行提示词」。

常用变量如下：

| 变量 | 含义 |
|---|---|
| `user_prompt` | 用户填写的任务提示词 |
| `issue_title` | 当前需求标题 |
| `project_path` | GitLab 项目的完整仓库路径 |
| `branch_name` | 任务使用的工作分支 |
| `base_branch` | 创建工作分支时使用的起始分支 |
| `target_branch` | Merge Request 的目标分支 |
| `task_mode` | 当前任务模式，值为 `execute` 或 `plan` |
| `require_changes` | 是否要求产生代码修改，值为 `true` 或 `false` |
| `previous_task_summaries_path` | 前序任务摘要文件的运行时路径 |
| `ci_failure_context_path` | CI 失败上下文目录的运行时路径 |

自由模式固定使用 `{{user_prompt}}`，不会显示运行指令编辑器。未知占位符会阻止保存或预览。自定义模板没有 `{{user_prompt}}` 时，当前任务提示词不会自动进入最终运行提示词。

### 让前序任务摘要进入上下文 {tips}

`{{previous_task_summaries_path}}` 只有在你把它写进模板时才会进入 Harness 上下文，内置实施和分析模板不会自动引用它。自由模式的模板固定为 `{{user_prompt}}`，没有位置加入摘要。具体做法见[《使用技巧》](/guide/78-techniques)。

## AI 模型服务与 Worker 配置

运行环境由需求和任务共同决定：

- Worker 由需求固定，创建任务时不能更换。
- Provider 默认跟随需求，也可以为本次任务指定一个覆盖值。
- Harness 是否可选由 Worker 配置和 Runtime Bundle 决定；续跑任务沿用当前 Harness，要切换请开启「使用新会话执行」。
- 「创建合并请求」是需求级设置。关闭时任务只推送工作分支，不创建 MR。

提交前确认 Worker 已验证。若配置被禁用、运行时未验证、Harness 不在当前 Runtime Bundle 中，表单会显示原因并阻止选择或提交。超过每日或每周用量上限时，任务也会被拒绝。

## Skills 与 MCP

Skills 可以跟随 Worker 默认值，也可以在本次任务中显式选择；显式选择会覆盖默认值，清空则不使用托管 Skill。Skills 要求挂载 Worker Kit 达到[《平台参考》](/guide/96-platform-reference)列出的最低版本，镜像内置模式不支持。

Skill 版本会冻结在任务快照中。目录更新后，任务详情页会标记旧版本或不可用，并提供应用当前版本的操作。MCP 不在任务里单独选择，CodeGraph 由 Worker Profile 的开关提供，也会随任务快照冻结。

发起任务前先确认 Worker 运行时状态为「已验证」。仍在验证时，到「系统配置」的「Worker」标签页完成验证。
