## 从哪里发起任务

任务的起点是需求。打开任一需求详情页，点击「创建任务」；需求下已有任务时按钮显示为「追加任务」。两者打开的是同一个创建抽屉「创建任务」，区别只在于这是该需求下的第一个任务还是后续任务。

也可以在「创建需求」页面（`/issues/create`）里直接填写需求并顺带发起第一个任务。旧路径 `/create-task` 会重定向到这里。

创建抽屉分为两块：「任务内容」描述目标并选择处理方式，「执行设置」确定任务优先级和执行时间。核心字段是「提示词」，也就是发给 Harness 的提示词：可以直接写，也可以点击「使用提示词模板」从模板库挑选，模板支持按标签筛选。选中模板会覆盖当前内容，界面会先弹出「当前描述内容将被模板替换，是否继续？」的确认横幅。

> [!tip] **快照边界**：创建任务时冻结不可变的 Worker 与模型服务快照；之后修改配置不会影响已创建的任务。

## 任务模式

首次创建时会先弹出「选择任务模式」，选定后才进入完整表单：

![模式决定是否改代码，时机决定何时排队](assets/diagrams/zh-CN/task-mode-choice.svg)

选定后可以在表单中通过「更改」重新选择。每种模式各自保留一份运行指令模板：在实施模式里改过的模板，切回来时还在；从未打开过的模式则使用自己的默认模板。

「要求代码变更」开关只对实施模式生效：开启后，若任务没有产生代码提交，则视为失败。新建任务时它默认关闭。切到分析模式或自由模式时该开关自动关闭并隐藏，因为这两种模式不承诺产生提交。

模式会被冻结在任务上，任务详情页的「任务模式」行显示最终值。重试会沿用源任务的模式；CI 自动修复任务固定使用实施模式并要求代码变更。

## 优先级

优先级有三档，界面上的三张卡片分别显示「P0」「P1」「P2」，卡片下方的说明文字是「紧急」「普通」「低优先级」：

- P0：线上阻塞或紧急问题，需要立即处理。
- P1：功能开发、改进和日常工作。
- P2：锦上添花、小型重构等可以稍后处理。

创建抽屉默认选中 P1。系统按 P0 → P1 → P2 的顺序取出任务；同一优先级内，已到期的预约任务优先于立即执行的任务，其次是预约时间更早、创建时间更早的任务。只有需求队列的队首参与派发：队首是 P2 的需求，只要其他需求还有 P0 或 P1 的队首在等待，就要继续排队。待执行任务（PENDING / QUEUED）可以随时通过「编辑任务」调整优先级。

## 立即执行或预约执行

「调度」区块决定任务何时进入执行队列，两个选项（立即执行 / 定时执行）的含义见上图。

选择了定时执行时，界面会给出「近7日预约热力图」：点击任意格子即可把该时段设为预约时间，颜色越深表示该时段任务越多。如果目标时段接近或达到容量上限，会提示「时段 {start}–{end} 已接近/达到满载（{count}/{max} 个任务）。」；管理员开启强制执行后，满载时段会直接拒绝创建，改期时同样会再查一次时段容量。

同一条需求队列内的预约时间受前后任务约束。新建任务时只受下界约束：下界取该需求所有活跃任务中最晚的预约时间，表单沿用界面文案提示「不得早于 Task #{source} 的最早执行时间」；给已有任务改期时窗口是双向的，界面会显示「Issue 队列可预约窗口：{min} – {max}」。时间统一按 UTC+8 展示，例如「该任务将在 {time}（UTC+8）执行。」

创建后仍可调整：待执行任务可用「立即执行」跳过等待，或用「修改预约」改到其他时间点。

## 运行指令与变量

「运行指令模板」是底层细节，默认折叠在「高级」里：它决定 Harness 实际收到的第一段指令，提示词只是其中的一部分。编辑器有「指令」和「预览」两个页签，「预览」按当前任务上下文渲染尚未保存的模板，点「刷新」可以重新生成；渲染结果会随任务保存，任务详情页的「最终运行提示词」展示的就是它。

常用操作：

- 「插入变量」：点击变量名，把它插入到文本框当前光标位置。
- 「恢复默认运行指令」：回到当前模式的默认模板。
- 「仅用提示词」：把模板换成 `{{user_prompt}}`。这个按钮出现在编辑平台默认模板的地方，即「系统配置」→「Worker」→「运行指令」。
- 未知占位符会被标出（「未知占位符：{names}」），后端也会拒绝保存或预览含未知占位符的模板；如果模板里没有包含用户提示词，会提示「当前运行指令不会自动包含需求内容」。

可用变量如下：

| 变量 | 含义 |
|------|------|
| `user_prompt` | 用户填写的任务需求内容 |
| `issue_title` | 当前需求的标题 |
| `project_path` | GitLab 项目的完整仓库路径 |
| `branch_name` | 任务使用的工作分支 |
| `base_branch` | 创建工作分支时使用的起始分支 |
| `target_branch` | 合并请求的目标分支 |
| `task_mode` | 当前任务模式：execute 或 plan |
| `require_changes` | 是否要求产生代码修改：true 或 false |
| `previous_task_summaries_path` | 历史任务摘要文件的运行时路径 |
| `ci_failure_context_path` | CI 失败上下文目录的运行时路径 |

自由模式固定使用内置的 `{{user_prompt}}` 模板，表单不为它显示运行指令编辑器，后端也会拒绝其他模板。渲染后的提示词会随任务冻结，任务详情页的「用户提示词」与「最终运行提示词」分别展示原始输入与最终结果。

### 让前序任务摘要进入上下文 {tips}

`{{previous_task_summaries_path}}` 指向一份记录本需求前序任务的文件，里面有每个任务的状态、目标、提交说明与执行摘要。实施模式与分析模式的内置模板都没有引用它，只有把占位符写进模板，摘要才会进入 Harness 的上下文。自由模式的模板固定为 `{{user_prompt}}`，没有位置放它。具体做法见《使用技巧》。

## AI 模型服务与 Worker 配置

「运行环境」区块显示这次任务用哪套 Worker 与模型服务：

- **Worker 由需求固定**：创建任务时不可更换，「Worker 与 Worker Kit 由需求固定」。
- **AI 模型服务可按需覆盖**：默认「跟随需求默认」，也可以「本次指定」一个 Provider；切换 Harness 时界面会提示已自动切换到协议匹配的 Provider。
- **Harness**：可选 Claude、Codex、Pi、OpenCode，可用性由 Worker 配置决定。状态会显示「可用」「不可用」「未验证」以及原因（如「Worker 配置已禁用」「运行时未验证」）。只有运行时包（Runtime Bundle）中实际提供的 Harness 才能选中，各条可用性原因的含义见《Harness 支持》。续跑任务必须沿用当前 Harness，勾选「使用新会话执行」后才可以切换。

「创建合并请求」是需求表单里的开关，控制这条需求是否产出 Merge Request；禁用时仅推送工作分支，不创建 MR，任务继承需求的选择。

## Skills 与 MCP

**Skills** 是可复用的技能包，由管理员维护，任务按需启用：

- 「跟随 Worker 默认值」：使用 Worker 配置里当前启用的默认 Skill。
- 显式勾选：本次选择会完整覆盖 Worker Profile 默认值；清空即可不使用任何系统管理的 Skill。

Skills 需要「挂载 Worker Kit」交付方式（0.3.5 或更高版本），「镜像内置（已过时）」不支持。任务创建后 Skill 会被冻结进快照，若之后全局 Skill 有更新，任务详情页会标注「旧版本」或「已不可用」，并可用「应用当前可用版本」刷新。

**MCP** 方面，Codify 内置的是 CodeGraph：Worker 配置中的「CodeGraph」开关会为使用该配置的任务启用本地 CodeGraph MCP 服务和项目索引。启用状态会随任务快照冻结，并在任务详情页的「任务快照」区块显示。

发起任务前请确认 Worker 运行时处于「已验证」状态；若仍在验证中，界面会要求先在「系统配置」的「Worker」标签页中点击「验证运行时」。
