## 访问管理与角色

**访问管理** 页面（`/access-management`）管理控制台用户、显式管理员覆盖、禁用账户和活跃会话，只有平台管理员可以打开。手动角色修改会覆盖该用户的引导用户名/组规则；禁用用户会立即撤销其活跃会话。

### 角色模型

平台上有两个角色：**平台管理员** 与 **平台用户**。**状态** 只有 **有效** 或 **已禁用** 两种。每个用户还带一个角色来源标签：**引导规则** 表示角色由 **管理员用户名** / **管理员 GitLab 组** 规则在登录时推导，**手动覆盖** 表示由管理员在此页面显式设置，**紧急入口** 表示该账户由 break-glass 登录创建。

强制引导只作用于来源为 **引导规则** 的用户。一旦在此页面保存过角色或状态，该用户就不再受用户名/组规则影响，直到再次改回。

### 用户列表

列表顶部给出 **已知用户**、**平台管理员**、**已禁用用户** 三个计数，**重新加载用户** 重新拉取数据。**按用户名、显示名或邮箱搜索** 与 **按角色筛选**、**按状态筛选** 组合过滤。

| 列 | 说明 |
|---|---|
| 用户名与显示名 | 当前用户额外显示 **当前用户** 标记 |
| **角色** | **平台管理员** 或 **平台用户** |
| **状态** | **有效** 或 **已禁用** |
| 来源 | **手动覆盖**、**紧急入口** 或 **引导规则** |
| **活跃会话** | 未过期、未撤销的会话数量 |
| **最近访问** | 最近一次会话活动时间，同时显示 **最近登录** |
| 身份 | **系统ID：{id}**、**GitLab ID：{id}** |

### 修改与撤销

**保存访问设置** 提交角色和状态的改动。为避免意外锁死，页面不允许修改你自己的角色和状态，对应行显示 **为避免意外锁死，这里不允许修改你自己的角色和状态。**。系统还会拒绝移除最后一个有效的平台管理员：如果改动会让平台管理员数量归零，保存失败。

**撤销会话** 立即失效该用户的全部活跃会话，成功后提示「已为 @{username} 撤销 {count} 个活跃会话」，没有会话时提示「@{username} 当前没有活跃会话」。撤销自己的当前会话请使用正常退出登录流程，页面会拒绝此操作。把某个用户设为 **已禁用** 会自动撤销其会话，之后该用户登录会被拒绝（HTTP 403，`User account is disabled`）。

Break-glass 账户使用 **紧急入口** 来源并固定为 **平台管理员**；它的启用与凭据由部署层的环境变量控制，正常运行时应保持关闭。

## 用量管理

**用量管理** 页面（`/usage-management`）查看用户用量并管理配额覆盖。用量按任务粒度统计，限制可以继承、单独覆盖，或设置为无限制。

### 限制模型

每个用户有四类配额，对应四个字段：**日 Token**、**周 Token**、**日任务数**、**周任务数**。每类配额有三种模式。

| 模式 | 含义 | 可用位置 |
|---|---|---|
| **继承** | 使用系统默认值 | 仅用户覆盖 |
| **自定义** | 使用本行填写的数值 | 系统默认值与用户覆盖 |
| **无限制** | 不做限制，界面上显示 **无限制** | 系统默认值与用户覆盖 |

**系统默认值** 只能选择 **自定义** 或 **无限制**，用 **保存默认值** 提交。**用户覆盖** 行可以选择 **继承**、**自定义** 或 **无限制**，用 **保存覆盖** 提交单行改动。顶部按键显示 **跟踪用户数**、**有覆盖的用户数**、**超限用户数**，并用 **日重置时间**、**周重置时间** 两个标签显示当前的配额重置时刻；筛选器提供 **全部用户**、**有覆盖**、**无覆盖**，被单独设置过的用户带 **已覆盖** 标记。

### 拦截点

配额在任务生命周期的两个位置强制执行，命中时会带上结构化的 `usage_limit_exceeded` 明细。

1. **创建任务**：超过任一项配额时，创建请求被拒绝（HTTP 409），任务不会写入。
2. **开始执行**：任务被调度执行前再次校验；此时任务会直接结束为 **失败**，错误信息为 `{"reason": "usage_limit_exceeded", "scope": "execute", "exceeded_items": [...]}`。

配额按日历窗口聚合：日配额统计当天写入 `TaskUsageLedger` 的累计值，周配额统计当周起始日之后的累计值。重置时刻显示在页面的 **日重置时间** 与 **周重置时间** 标签上。

## 系统统计

**系统统计** 页面（`/system-statistics`）给出系统全生命周期的运营参考统计，覆盖当前保留数据，以及自覆盖起点起通过标准删除入口保留的删除数据。页面顶部提供 **刷新**、**最后刷新：{time}** 与 **报表时区：{timezone}**。

### 过滤与覆盖

**趋势时间范围** 可选 **全部**、**近 90 天**、**近 1 年**。**数据状态** 可选 **全部**、**当前保留**、**已删除**。**覆盖说明** 显示 **参考统计：仅覆盖当前仍保留的数据，以及从 {capture} 起通过标准删除入口保留的删除数据。**；尚未启用删除数据留存时显示 **删除数据覆盖保证尚未启用**。**数据说明** 明确本页是运营参考统计，不构成计费、审计或容量结算依据，覆盖起点之前已删除的数据无法恢复，已删除 Task 仅展示脱敏快照、不提供详情链接。

### 统计分区

| 分区 | 内容 |
|---|---|
| **当前运行态** | **待执行**、**排队中**、**运行中**、**长时间运行**、**活跃需求**、**平均排队时长** 与 **样本数**，基于当前业务表实时聚合 |
| **生命周期累计** | **历史 Task 数**、**历史需求数**、**已完成**、**失败**、**已取消**、**已结束**、**成功率**、**失败率**、**含 MR 需求**、**已知 Token 数**、**已知代码变更**、**已知执行时长**、**平均执行时长**、**执行时长样本数**、**已删除 Task**、**已删除需求**、**未终态删除** |
| **数据覆盖率** | **Token 覆盖** 与 **代码变更覆盖**，按 **合格样本**、**完整样本**、**部分样本**、**缺失样本**、**已记录** 与 **覆盖率** 展示 |
| **基础趋势** | **Task 创建**、**Task 结束**、**Task 删除**、**需求创建**，按报表时区分桶 |
| **基础 Breakdown** | **项目**、**Provider**、**Harness** 与 **Task 模式 Breakdown**，高基数维度只展示主要分组 |

未知的 Token 或代码变更值不参与平均值与总量计算，并在覆盖率中单独展示。**Token 覆盖** 的合格样本是已进入终态且有开始时间的 Task；**代码变更覆盖** 的合格样本是已完成的实施模式和自由模式 Task。

## 数据清理

**系统数据清理** 是维护操作选项卡中的删除入口，按 Issue 删除旧的系统记录及其任务数据。删除以 Issue 的创建时间为准：**清理 N 天以前的数据** 接受天数（必填，单位为 **天**），更早创建的 Issue 会成为候选。

### 活跃与强制

只要 Issue 仍有 **待处理**、**已入队** 或 **运行中** 的任务，或者任务仍保留容器引用，该 Issue 就会被跳过，只累加 **跳过 {skipped} 个活跃 Issue**。**强制清理活跃任务** 针对任务状态已不可信的场景，也会删除 pending、queued 和 running 任务记录，并尽力停止正在运行的容器。

两条确认路径对应两种模式：**确认清理符合条件的 Issue 数据吗？此操作不可撤销。** 与 **确认强制清理符合条件的数据，包括活跃任务吗？运行中的容器会尽力停止。**。强制模式下，如果容器停止失败，该 Issue 会被整体跳过，不会留下半删状态。完成后提示 **清理完成：已删除 {issues} 个 Issue、{tasks} 个任务，跳过 {skipped} 个活跃 Issue。**

### 清理范围

一次成功的清理会按顺序处理以下对象。

1. 在删除前把该 Issue 的生命周期统计封存为删除快照，并记录操作人。
2. 删除任务日志、payload、原始日志块、摄取游标、运行归档记录、用量账本与 Mattermost 投递记录。
3. 删除 Issue 执行锁，并把 Webhook 事件行的 Issue 引用置空而不是删除事件。
4. 删除 Issue 与 Task 记录，并清理不再被引用的 Skill 版本。
5. 删除运行归档文件，并尽力删除远程 Issue workspace。

容器清理失败、归档文件缺失或 workspace 删除失败都会记录在结果中，不会中断整批操作。workspace 的自动回收以 **Workspace 保留天数** 为准，运行归档以 **运行归档保留天数** 为准，两者都不删除任务或需求本身。

## 维护

**维护操作** 选项卡承载两类维护工作。

### 操作

**操作** 分区提供 **重新加载** 与 **重置为环境变量/默认值**。

**重新加载** 重新拉取当前生效配置，用于确认其他管理员刚保存的值。**重置为环境变量/默认值** 会将所有配置项重置为环境变量/默认值，未保存的修改将会丢失（确认文案：**将所有配置项重置为环境变量/默认值？未保存的修改将会丢失。**）。重置只影响持久化的运行时配置覆盖，不会删除用户、任务或历史数据。

### 密钥与缓存维护

维护类操作还分散在对应的配置选项卡中：**清除已存储 OIDC 密钥**、**清除已存储 GitLab Bot Token**、**清除已存储 GitLab Admin Token**、**清除已存储 Anthropic API Key**、**清除已存储 Mattermost Bot Token**、**清除已存储告警 Webhook** 用于撤销服务端保存的敏感值，**清除项目缓存** 用于让 GitLab 项目列表重新拉取。

### 部署约束

以下项目不能在页面上修改，必须在部署层处理。

| 项目 | 说明 |
|---|---|
| `WORKER_WORKSPACE_HOST_PATH` | Worker 本地 Workspace 路径；修改后需要重新创建 Backend 与 Scheduler |
| `CONFIG_ENCRYPTION_KEY` / `SECRET_KEY` | 密钥与会话签名的根密钥；更换或丢失会导致已存储密钥无法解密 |
| Worker 镜像与 Worker Kit | 变更后必须重新进行 Profile 运行时验证，并在真实 Docker Host 上跑最小任务验证 |
| 数据库迁移 | Scheduler 在启动阶段执行 `alembic upgrade head`，Backend 固定 `AUTO_MIGRATE=false` |

生产环境不要执行 `docker-compose down -v`：它会删除 PostgreSQL volume，等价于重置数据库，运行时配置、用户、会话和审计日志会一并丢失。
