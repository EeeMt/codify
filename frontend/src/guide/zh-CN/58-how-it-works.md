本章从内向外建立一套心智模型：先看负责预测下一个 token 的大模型，再看把预测变成代理回合的 Harness，最后看让回合具备持久性、可观测性和交付路径的 Codify。这里解释的是职责边界和整体机制，具体实现仍可继续阅读 [Harness 支持](/guide/65-harness-support) 与 [交付内部机制](/guide/75-delivery-internals)。

## 总图：从 token 到改动

同一次运行可以从三层来理解。大模型回答“下一步可能是什么”，Harness 把这个答案放进一个有用的循环，Codify 则为循环提供任务、Worker、时间线和交付路径。

| 层次 | 核心问题 | 负责什么 |
|---|---|---|
| 模型层 | 下一步应该是什么？ | token 概率、上下文处理和解码 |
| Harness 层 | 这一回合如何继续推进？ | 指令、工具调用、会话状态、技能和事件归一化 |
| Codify 层 | 如何把工作变成持久的交付？ | 需求、任务、快照、调度、Worker、证据和 Git 交付 |

可以先阅读 [概念](/guide/20-concepts)，再深入 [Harness 支持](/guide/65-harness-support)，最后回到日常交付流程 [交付](/guide/50-delivery)。

## 大语言模型做什么

大语言模型接收一串 token：它们可能是单词、标点，也可能是更小的文字片段。模型在有限的上下文窗口中处理这串序列，为可能出现的下一个 token 计算分数。解码过程再根据这些分数选出一个 token，把它追加回上下文，然后再次运行模型。这个循环不断重复，就会生成回答、代码块，或者像工具调用这样的结构化请求。

Transformer 是这个过程背后的高层机制。注意力机制让模型能够衡量当前上下文中不同 token 之间的关系，训练得到的参数再把这些关系转换为概率分布。模型不会凭空读取一份持久的对话记忆：对于当前请求，它能使用的内容必须在宿主提供的上下文里，同时还要受模型和 Provider 的限制。

采样设置会改变如何从概率分布中解码。更确定的选择通常倾向于最高分的后续内容；更多变化则可能探索分数较低的选择。无论采用哪种设置，模型都没有直接修改仓库的权限。模型可以输出工具调用请求，但必须由宿主校验并执行，再把观察结果返回给它。

> [!info] 一个重要边界：模型提出下一段输出，但不负责文件系统、Shell、会话或最终提交。

## Harness 增加了什么

Harness 是让一次编码回合持续推进的宿主。它把模型、系统指令、当前提示词、对话历史、Provider 协议、工作区工具、会话状态和能力策略组合在一起。在 Codify 中，Claude、Codex、Pi 和 OpenCode 都由各自的适配器接入同一份契约，同时保留自己的 CLI 和线协议特点。

核心循环并不复杂，但边界很关键：Harness 把上下文发送给模型；模型返回文本或工具请求；Harness 检查请求并执行获准的工具；工具产生观察结果；Harness 再把观察结果放回下一次模型请求。技能可以为环境增加可复用的指令或工具，能力门控则可以关闭不支持的实时控制、后续指令或子代理能力。

会话让支持继续执行的 Harness 能够跨任务延续这条循环。事件和结果归一化则让 Codify 可以用稳定的方式展示模型输出、工具活动、用量、完成和失败，即使底层 CLI 各不相同。任务模式仍然属于任务本身：「实施」「分析」和「自由发挥」描述本回合要追求的结果，并不是三种不同的模型。

适配器操作、Provider 协议配对、会话目录、技能和各 Harness 的能力差异，详见 [Harness 支持](/guide/65-harness-support)。

## Codify 增加了什么

Codify 把 Harness 循环放进一个持久化的控制平面。需求保存长期有效的背景，以及工作区、会话和分支。每一次具体推进都成为一条有序任务，携带提示词、模式、会话选择和执行身份。任务创建时，Codify 会解析 Worker Profile，并绑定任务快照与不可变的 Runtime Bundle，因此后续的配置变化不会改写已经存在的任务。

调度器决定任务何时可以运行，同时处理并发容量和同一需求内的顺序，然后启动隔离的 Worker 容器。Worker 准备仓库，挂载冻结的运行时和需求共享状态，调用选中的 Harness，并把归一化事件投影到任务时间线。执行结束时，Codify 记录结果、提交、用量、运行统计和归档证据；开启交付后，再发布工作分支并创建或更新 Merge Request。

在这张图里，Codify 不会变成另一个模型。它围绕模型编排 Provider、Harness、工作区和 Git 生命周期。用户侧的创建流程见 [创建任务](/guide/30-create-task)；队列行为见 [调度](/guide/60-scheduling)；证据和运行观察见 [可观测性](/guide/70-observability)；最终发布与归档边界见 [交付内部机制](/guide/75-delivery-internals)。

## 三层如何合起来

三层回答不同的问题，也交接不同的产物。保持这个区分，既能更清楚地解释产品行为，也能让问题定位更准确。

| 层次 | 输入 | 主要动作 | 输出 | 主要负责方 |
|---|---|---|---|---|
| 模型层 | 上下文 token 和生成设置 | 预测并解码下一个 token | 文本或结构化工具调用建议 | 模型 Provider |
| Harness 层 | 提示词、历史、Provider、工作区和策略 | 执行代理回合并运行获准工具 | 观察结果、归一化事件和最终结果 | Harness 适配器/运行时 |
| Codify 层 | 需求、任务快照、Runtime Bundle 和调度状态 | 编排、隔离、观测并交付 | 任务证据、提交、分支状态和 Merge Request | Codify 控制平面与 Worker |

不要让下层解释上层的决策。模型可以帮助解释为什么生成了某段文字，却不能解释任务为什么在队列里等待；Harness 可以解释工具请求为什么被拒绝，却不能解释分支发布为什么失去了租约。Codify 可以把这些记录连接成一条时间线，但不会抹掉各层的职责边界。

## 出现问题时从哪里查

先根据症状定位，再检查真正拥有它的层：

| 症状 | 首先观察 | 可参考的指南 |
|---|---|---|
| 回答偏题、不完整，或缺少上下文 | 提示词、模型、Provider 和上下文窗口 | [创建任务](/guide/30-create-task) |
| 工具没有执行、会话无法继续，或协议被拒绝 | Harness 适配器、能力门控、会话或技能物化 | [Harness 支持](/guide/65-harness-support) |
| 任务一直等待、容器失败、事件缺失，或提交/Merge Request 没有交付 | 调度器、Worker 运行时、事件投影或交付状态 | [调度](/guide/60-scheduling)、[可观测性](/guide/70-observability)、[交付内部机制](/guide/75-delivery-internals) |

这套观察角度能让排查保持聚焦，同时保留跨层追踪的路径：质量问题先看模型和提示词，执行问题看 Harness，编排与交付问题看 Codify。确认责任层后，再用相关章节中的字段、日志和状态转换完成验证。
