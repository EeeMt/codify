## 上下文跟着需求走

任务永远挂在需求下，需求持有三样跨回合延续的东西：工作区、AI 会话和工作分支 `codify/issue-{id}`。追加任务共享这三样。

追加任务会继承的内容，以及不继承的内容：

| 继承项 | 行为 |
|--------|------|
| 工作区 | 同一份按需求隔离的工作副本，同一条分支；回合之间不会重新克隆 |
| 会话 | Harness 的对话，前提是任务保持默认的「继续会话」，且需求与会话线代里仍记录着会话；任务详情页的「会话模式」行会显示最终值 |
| 前序任务摘要 | 记录本需求更早回合的文件，每次运行都会写入容器；只有在运行指令里引用它，模型才会看到 |
| 提示词与运行指令 | 每个任务都是新的，不继承 |

「使用新会话执行」是唯一会切断对话、同时保留其余状态的开关，提示为「不继承当前对话上下文；保留工作区、Git 分支和旧会话记录。」需求转向别的问题、不再需要这段对话，或者要换成另一个 Harness 时都用得上：续跑任务必须沿用原 Harness。

重试时也要做同样的取舍：「会话策略」提供「续接当前会话」与「新开一代会话」；当重试源属于比当前队列更旧的会话线代时，Codify 会要求改用全新会话，而不是接着一段已经对不上的对话。

要拿到彼此独立的工作区、分支与会话线代，只能新建需求。下一个回合要接着你此刻手上的代码与对话往下做，就追加；否则新建一个需求。

## 只看不改的探索

「分析模式」适合检查一条正在使用的分支，而不改动它。运行产生的修改会在结束时被丢弃，任务仍然算成功：分析模式不要求产出提交，`require_changes` 固定为 false，也不会为该任务记录任何提交。

因此它适合那些要基于真实代码回答、又不能让分支发生变化的问题：现有实现是怎么做的、某个方案能不能落地、失败出在哪一步。分支停在原处，同需求随后的实施任务从同一个 tip 继续。

## 组合使用三种任务模式

任务模式按任务保存，所以同一条需求的多个回合可以用不同模式。

| 模式 | 运行指令 | 运行结束时的改动 | 交付 |
|------|----------|------------------|------|
| 实施模式 | 该模式的默认模板，或你提交的模板 | 由 Worker 提交 | 推送分支，创建或复用 Merge Request |
| 分析模式 | 该模式的默认模板，或你提交的模板 | 丢弃 | 不推送 |
| 自由模式 | 固定为 `{{user_prompt}}` | 由 Harness 决定 | 只有运行产出了提交才会创建 Merge Request |

自由模式会拒绝除 `{{user_prompt}}` 以外的任何模板，Harness 收到的是未经包装的需求原文。当「由 Harness 自己判断是回答、分析还是改代码」才是目的时用它，并接受这次运行可能没有东西可以合并；「要求代码变更」关闭时，这个结果就是成功。「要求代码变更」只对实施模式生效，开启后，没有产生提交的实施任务会判为失败。

一个常见的顺序是先跑分析模式，把问题和改法定下来，再用实施模式在同一条分支上落地。每种模式各自保留一份模板：在实施模式里改过的模板，切回来时还在，也不会被套用到你没动过的模式上。

## 把前序任务摘要带进上下文

每次运行 Codify 都会为属于某条需求的任务在容器内写一份摘要文件，路径是 `/tmp/codify-runtime/previous-task-summaries.md`，在运行指令里以 `{{previous_task_summaries_path}}` 暴露。实施模式与分析模式的内置模板都没有引用它，不自己加上这个占位符，文件就一直不会被读到。

做法是在任务表单里展开「高级」，编辑实施模式或分析任务的「运行指令模板」，把 `{{previous_task_summaries_path}}` 放在需要回看前几轮的位置，再用「预览」确认渲染结果。渲染后的提示词会随任务存储，事后也能核对 Harness 实际收到的内容。自由模式加不了这个占位符，它的模板只能是 `{{user_prompt}}`。

文件开头是需求的标题与描述，之后是这条需求前面每个任务的条目，包含状态、目标、提交说明与执行摘要；没有前序任务时文件会说明这一点。要的是对话本身，用「续接当前会话」。

## 跨越需求继续推进

「起始分支」不做过滤，项目里的任何分支都能选中，其他需求的 `codify/issue-{id}` 也一样。新需求的工作分支就从这条分支的当前 tip 派生：首个任务克隆所选分支，再基于它的远端 tip 执行 `git checkout -b`。源需求不要求已经合并或关闭，代码路径也不读取它的状态，从未跑过的源需求同样可以。

不会跟着过来的东西：

- **只有提交。** 新需求有自己的工作区、自己的会话线代和自己的任务历史。
- **两个 Merge Request 互不相干。** 每条需求按自己的分支维护 MR。

会出问题的地方：

- **源分支没了。** 新需求的第一个任务运行时如果这条分支已经不存在，Codify 会打印一条警告，退回到项目默认分支，任务照常成功，只是预期的改动不在里面。在新需求跑过之前就用「关闭并删除分支」关掉源需求，最容易走到这一步；先让新需求跑一次，再清理旧分支。
- **合并目标指向默认分支。** 该字段预填项目默认分支，于是新需求的 MR 会把源需求尚未合并的提交一并带进那个分支，因为它们是新分支的祖先。如果这不是你要的结果，把合并目标改到源分支，或者先把源需求合并掉。
- **推送权限是 GitLab 的事。** Codify 不管理受保护分支；匹配 `codify/*` 的受保护分支规则会同时挡住机器人和你。

## 与 Codify 共用同一条分支

`codify/issue-{id}` 就是一条普通的远端分支，你的提交和 Worker 的提交一样属于它。远端领先于工作区时，Codify 会把工作区快进到你的 tip，下一个回合从这里继续。交付阶段会在推送前重新观察远端的当前位置，并以它作为 `--force-with-lease` 的比对基准，所以运行途中你自己推上去的提交会被拒绝，而不会被覆盖。

历史必须保持一条直线。本地与远端分叉、远端回退、远端分支被删除而工作区还记得它，以及工作区带着未提交改动时远端又前进了，这些都会被拒绝：任务在 Harness 启动前的仓库准备阶段就失败，两边都不会被覆盖。浅克隆下有些祖先关系无法判定，同样按拒绝处理。往上加新提交没问题，改写分支不行。

要把工作挪到别的分支上，Codify 内部没有跨分支复制的办法。这些提交就是普通的 git 历史，需要时在你自己的环境里从这条分支 cherry-pick。
