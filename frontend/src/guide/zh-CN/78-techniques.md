## 上下文跟着需求走

同一需求会把工作区、AI 会话和工作分支 `codify/issue-{id}` 从一条任务带到下一条任务。

| 会继承 | 不会继承 |
|---|---|
| 工作区和分支 | 新任务提示词 |
| 继续会话的对话 | 新任务运行指令 |
| 前序任务摘要文件（运行指令引用时） | 各模式的本次输入 |

对话已经无助于判断，或需要换 Harness 时，选择「使用新会话执行」。工作区、分支和旧会话记录仍会保留；续接任务必须沿用当前 Harness。

重试也可以在「会话线代」中选择。源任务比当前队列末尾更旧时，系统可能要求新开一代会话。要获得独立的工作区、分支和会话线代，只能新建需求。

## 只看不改的探索

「分析模式」在真实分支上检查代码，运行结束时丢弃改动。它不要求提交，且「要求代码变更」固定关闭。适合用来了解实现、调查失败或比较方案，再追加实施任务。

## 组合使用三种任务模式

模式保存在 Task 上，同一需求可以混用三种模式：

| 模式 | 预期结果 | 交付 |
|---|---|---|
| **实施模式** | Worker 提交改动 | 推送分支并交付 MR |
| **分析模式** | 只报告，不改变分支 | 不推送 |
| **自由模式** | Harness 自己决定回答、检查还是编辑 | 只有产生提交时才有 MR |

自由模式的运行指令固定为 `{{user_prompt}}`。「要求代码变更」关闭时，即使没有提交也算成功。常见做法是先分析，再在同一条分支上实施。

## 把前序任务摘要带进上下文

每次需求运行都会写入 `/tmp/codify-runtime/previous-task-summaries.md`，并通过 `{{previous_task_summaries_path}}` 暴露路径。内置实施和分析模板不会引用它，需要时自行加入占位符；自由模式的模板固定，不能加入。

展开「高级」，编辑对应模式的「运行指令模板」，加入占位符，再用「预览」检查。渲染后的提示词会保存到任务上。摘要文件包含需求标题和描述，以及前序任务的状态、目标、提交说明和执行摘要。

## 跨越需求继续推进

「起始分支」可以选择项目中的任意分支，包括其他需求的 `codify/issue-{id}`。新需求会获得新的工作区、会话线代和任务历史，只有该分支的提交会带过去。

注意三种情况：

- 新需求第一次运行前源分支已被删除时，仓库准备会退回项目默认分支并记录警告。清理源需求前，先让新需求运行一次。
- 新需求的「合并目标」默认是项目默认分支。源需求的提交暂时不该进入默认分支时，应把目标改为源分支。
- Codify 不管理 GitLab 的受保护分支规则。匹配 `codify/*` 的规则可能同时阻止机器人和你的推送。

## 与 Codify 共用同一条分支

工作分支就是普通远端分支，你的提交可以被下一条任务使用；远端领先时，Codify 会把工作区快进到远端位置。

交付前 Codify 会重新获取远端位置，并用它作为 `--force-with-lease` 的比对值。运行期间有人推送时，当前推送会被拒绝，不会覆盖对方。历史分叉或回退、远端分支被删、浅克隆无法确认祖先关系，或本地未提交改动遇到已前进的远端时，也会拒绝。

Codify 没有跨分支复制操作。需要移动提交时，在自己的 clone 里使用普通 Git 命令，例如 cherry-pick。
