## 任务失败

任务详情页的 **错误** 卡片显示 **任务执行器最近一次上报的失败信息**，包含 **失败原因** 与 **失败类型**；**显示完整输出** 展开原始错误。失败类型取值固定为 **超时**、**协议错误**、**已取消**、**认证失败**、**限流**、**沙箱失败** 和 **Harness 错误**。**监控** 页面的 **最近失败任务** 列表会先暴露首行错误，便于快速定位。

### 常见失败签名

下表中的文本来自后端写入的任务错误信息，可在任务详情页或数据库中对照。

| 错误信息特征 | 含义 | 处理方式 |
|---|---|---|
| `Task timed out after <n>s` | 超过该任务 **本次超时上限**；任务开始执行时冻结上限，运行中不会切换 | 查看 **执行截止时间**，调整 **高峰超时（秒）** / **低峰超时（秒）**，或把任务拆小 |
| `protocol_error: ...` | Worker 上报的规范事件与进程状态矛盾：缺少终态、`run.completed` 与退出码冲突、`git_delivery` 被拒或出现未知终态 | 直接重试；若重复出现，用运行归档核对 Worker 侧事件 |
| `{"reason": "usage_limit_exceeded", ...}` | 配额拦截。`scope` 为 `execute` 表示任务在执行前被拦截并标记为失败 | 在 **用量管理** 调整系统默认值或该用户覆盖 |
| `{"code": "worker_runtime_unavailable", ...}` | Task Snapshot 指定的 Worker Kit 或 Runtime Bundle 在目标主机不可用 | 恢复运行时后 **重新检查此 Task 的运行时**，或取消该 Task |
| `{"code": "harness_cli_unavailable", ...}` | 任务选定的 Harness CLI 不在 Kit 的 inventory 中 | 重建或安装包含该 CLI 的 Kit，再重新验证 Profile |
| `{"code": "worker_runtime_check_failed", ...}` | 调度前的 Worker Kit 运行时检查失败 | 检查 Kit 路径与挂载；重试不会绕过该检查 |
| `{"code": "execution_contract_mismatch", ...}` | Snapshot、attempt schema 与 Runtime Bundle 契约不一致 | 修复 Profile 与 Bundle 组合后重建任务 |
| `Task was running when scheduler restarted (container not found)` | 崩溃恢复在可达的 Docker daemon 上确认容器不存在 | 任务已按失败收敛，按需重试 |
| `Container disappeared during resume: ...` | 恢复监控时容器消失 | 任务已标记为失败，检查 daemon 与容器日志 |
| `Worker failed to start: <异常>` | 容器启动失败，通常是镜像、挂载或 Docker 连接问题 | 在 **监控** 页面的 **容器排障** 选项卡查看 **Docker 目标** 状态 |
| `Task <id> is RUNNING without started_at` | 运行时字段不一致，任务被强制标记为失败 | 属于数据异常，保留现场后重试 |
| `Cancelled by user` | 用户主动取消，不是故障 | 无需处理 |

失败信息在写入前会经过敏感数据脱敏，`glpat-*` 令牌与 `sk-ant-*` 密钥不会出现在日志或错误摘要中。

### 失败之后

- **重试** 重新入队当前任务，沿用原 Task Snapshot。
- **追加任务** 在同一 Issue 下创建后继任务，共享工作区、AI 会话与 Git 分支。
- **重新检查此 Task 的运行时** 只对因 Worker 运行时不可用而阻塞的任务有意义；检查成功后调度会自动恢复。
- **手动修正** 可把任务标记为 **标记为失败** 或 **标记为成功**，并可填写 **修正原因（选填）**；修正会影响统计与 Issue 状态，被修正过的任务显示 **已手动修正**。

如果任务长期停在 **待处理** 而不是失败，请先看下一节。

## 容器与调度异常

**监控** 页面（`/monitor`）的三个选项卡分别对应 **运行概览**、**容器排障** 和 **健康信号**，容器排障页直接列出缺口与孤儿。

### 缺口与孤儿容器

| 指标 | 含义 |
|---|---|
| **任务/容器缺口** | 运行中任务当前没有看到对应的运行中容器 |
| **孤儿容器** | 运行中容器当前没有对应的运行中任务 |
| **可见容器** | 后端返回的全部工作容器，包括非运行态 |
| **已关联实时容器** | 仍与运行中任务对应的运行态容器 |

工作容器清单中的 **对应关系** 列会标出 **已关联**、**未映射**、**任务缺失**、**容器晚于任务结束**、**任务仍标记为运行中** 或 **历史记录**。容器名遵循 `codify-<task_id>-issue<issue_id>` 形式（前缀由 `worker_container_prefix` 决定）。**部分 Docker 目标当前不可用** 出现时，该 daemon 上的容器既不会被当作孤儿清理，也不会被误判为缺失，恢复会延迟重试。

### Scheduler 重启后的行为

Scheduler 启动时会运行崩溃恢复，按以下规则收敛状态。

1. 容器在运行且任务为 RUNNING：恢复监控。
2. 容器已退出但任务为 RUNNING：仍恢复该任务，并从已退出的容器收集日志与结果。
3. 存在容器但没有匹配的运行中任务：作为真正的孤儿删除。
4. 任务为 RUNNING 但没有容器：任务标记为 **失败**，错误信息为 `Task was running when scheduler restarted (container not found)`。

任务恢复使用不可变的容器 ID，而不是容器名；因此即使部署时改过容器名前缀，存活中的 Worker 也不会被隐藏。恢复期间若 daemon 不可达，任务会保持 RUNNING 并以后台重试方式继续等待，而不是被误判失败。

### 任务不被调度

看板与队列上下文会直接说明原因：

| 界面提示 | 原因 |
|---|---|
| **队首 · 等待 Worker** | 已到执行时间，但没有空闲并发额度 |
| **队首 · Worker 运行时不可用** | Task Snapshot 指定的运行时在该主机不可用 |
| **等待 Task #{blockedBy} 清理工作区** | 前序任务的 workspace 尚未回收 |
| **排队第 {position} 位 · 等待 Task #{blockedBy}** | 同一 Issue 的回合顺序尚未轮到 |
| **回合序号需修复** | 该 Issue 的回合序号需要人工修复，调度暂不可用 |

其他常见阻塞点：**最大并发数** 已被占满；同一 Issue 的互斥锁仍在；任务设置了未来的 **预约时间**；**强制执行时段限制** 开启且目标时段已满（创建时被拒绝）。

如果所有任务都停在 **待处理** 且没有任何上述提示，按顺序检查：Scheduler 是否在运行、Backend 与 Scheduler 日志是否有异常、数据库中任务是否停留在 PENDING/QUEUED、`MAX_CONCURRENCY` 是否被设得过低。**监控** 页面的 **容器排障** 选项卡中的 **队列压力** 与 **系统健康度** 卡片可以快速判断是容量问题还是对齐问题。

## 权限与登录问题

### 登录被重定向

前端收到 401 会清空会话并跳回登录页，页面顶部按原因给出提示：

| 提示 | 触发条件 |
|---|---|
| 您的会话已过期或尚未登录，请重新登录以继续。 | 未登录或会话已失效 |
| 会话已过期，请重新登录。 | 会话超过 **Session TTL（秒）** |
| 会话已被撤销，请重新登录。 | 会话被管理员撤销或被禁用账户连带撤销 |
| 访问被拒绝，请使用有权限的账号登录。 | 已登录但当前页面无权限 |
| 请登录以继续。 | 其他需要登录的入口 |

GitLab 侧令牌刷新失败时会返回 401 并要求重新登录（`GitLab login expired and refresh failed. Please sign in again.`），这不是 Codify 会话问题，重新走一次 GitLab 登录即可。

### 403 无权限

| 错误 | 原因 | 处理 |
|---|---|---|
| `Admin access required` | 非平台管理员访问 **系统配置**、**访问管理**、**用量管理** 或 **系统统计** | 由管理员在 **访问管理** 提升角色 |
| `Access to this page is restricted` | 共享页面（Monitor / Schedule Overview / Analytics）未对普通用户开放 | 在系统配置的 **运行与共享** 选项卡里，打开 **页面权限** 下的对应开关 |
| `User account is disabled` | 账户处于 **已禁用** 状态 | 在 **访问管理** 恢复为 **有效**，否则无法登录 |
| `You may only operate on your own tasks unless you are an admin` | 普通用户操作他人的任务 | 使用任务发起人或管理员账户 |

在 **访问管理** 中，你不能修改自己的角色与状态，也不能移除最后一个有效的平台管理员；这两条限制用于避免把自己锁在系统外。

### OIDC 与紧急入口

登录页在 OIDC 未启用时显示 **OIDC 登录尚未启用，当前控制台认证处于绕过状态。**；启用后使用 **使用 GitLab 继续**，需要本地兜底时可用 **使用密码登录** 或 **紧急访问**（**紧急用户名** / **紧急密码** / **使用紧急访问登录**）。**紧急管理员入口已启用。请仅在 OIDC 恢复或管理员被全部锁定时使用。** 是预期的安全提示；该入口受环境变量控制，未启用时登录请求返回 503。

排查 OIDC 配置按以下顺序：

1. 在系统配置的 **认证与会话** 选项卡使用 **测试 OIDC 连接**，确认 issuer 发现成功并核对返回的 scopes。
2. 查看 **OIDC 诊断** 面板的 **检查项**：发现、回调地址、必需 scopes、Cookie 策略。
3. 处理 **运维告警**：回调地址路径不是 `/api/auth/callback`；HTTP 与 **Cookie Secure** 不匹配；**Session TTL** 超过 24 小时；SameSite=None 搭配非安全 Cookie；启用了组管理员引导但 GitLab 未返回 groups。
4. 确认 GitLab OAuth 应用允许 `openid`、`profile`、`email`、`read_api`，且 **回调地址** 与部署地址完全一致。

配置保存失败并提示解密或加密错误时，问题在部署层：`CONFIG_ENCRYPTION_KEY` 或 `SECRET_KEY` 被更换，导致数据库中的密钥无法解密。恢复原密钥后重新保存即可。

## 常见问题

### 任务创建成功但一直不执行

依次确认 Scheduler 进程在运行、`MAX_CONCURRENCY` 没有被设得过低、任务没有停留在 PENDING/QUEUED、没有同 Issue 的互斥任务、没有配置未来的 **预约时间**。

### 创建任务被拒绝，提示时段已满载

**强制执行时段限制** 已开启，且目标小时时段的预约数达到 **每小时时段最大任务数**。提高上限、关闭强制（改为仅警告）或换一个时段预约。

### 普通用户看不到共享页面

**允许平台用户访问 Monitor**、**允许平台用户访问 Schedule Overview**、**允许平台用户访问 Analytics** 三个开关默认关闭，需要在 **页面权限** 中分别开启。开启后普通用户只看到自己可访问项目范围内的数据。

### 任务中断，前端日志不完整

先确认任务详情页是否拿到了实时日志，再检查 Backend / Scheduler 日志中是否有异常，以及 Worker 容器是否被提前退出。归档完成后可下载运行归档核对完整原始记录。

### 重启 Scheduler 会不会杀掉正在跑的任务

不会主动杀。恢复逻辑会重新接管仍然存在的容器；只有确认容器不存在时，任务才会以失败收敛，错误信息为 `Task was running when scheduler restarted (container not found)`。

### 容器比任务活得久，是异常吗

多数情况是收尾中的延迟清理或历史记录。**监控** 页面的 **容器排障** 选项卡会把真正需要处理的项单独列在 **孤儿运行中容器** 下，并区分 **容器晚于任务结束** 与 **任务仍标记为运行中**。

### 如何轮换已保存的密钥

在每个配置项输入新值并保存；要把服务端保存的值彻底撤销，使用对应的清除按钮（例如 **清除已存储 OIDC 密钥**）。轮换后记得更新依赖这些令牌的外部系统。

### 如何安全清理历史数据

优先用 **系统数据清理** 按 Issue 删除，它会跳过仍有活跃任务的 Issue，并在删除前封存生命周期统计。只有确认任务状态已不可信时才使用 **强制清理活跃任务**，因为它会尽力停止正在运行的容器。

### OIDC 配置突然失效

检查 `system_config` 是否仍有数据、PostgreSQL volume 是否被重建、`CONFIG_ENCRYPTION_KEY` 是否变化、OIDC Client Secret 是否仍能正确解密。生产环境不要执行 `docker-compose down -v`。

### 前端页面打不开

确认 nginx 已启动、Backend 健康、浏览器访问的是前端端口（默认 8880），并可用 `/health` 检查后端。
